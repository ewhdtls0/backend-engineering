# 상품 가격 변경 이력 조회 코드리뷰

리뷰 일자: 2026-09-11

## 검증 결과

`./gradlew.bat test --no-daemon` 실행 결과: 9개 테스트 모두 통과.

## 잘 구현한 점

- `@Transactional`로 가격 변경과 이력 생성을 하나의 작업으로 묶었다.
- 가격 비교에 `BigDecimal.compareTo`를 사용해 `39000`과 `39000.00`을 같은 금액으로 처리한다.
- `Product.changePrice`로 상태 변경 책임을 엔티티에 뒀다.
- 이력 조회 쿼리는 상품 ID, 선택 기간, 최신순 정렬(`changedAt DESC`, `id DESC`)을 모두 처리한다.
- `from > to`를 400으로 처리하고, 입력 오류와 미존재 상품을 일관된 API 오류 응답으로 변환한다.

## 테스트 개선 사항

### [P1] 내가 작성한 롤백 테스트가 트랜잭션 누락을 실제로 검출하지 못한다

내가 만든 테스트는 이력 INSERT가 실패하게 만든다. 현재 서비스는 `PriceHistory`를 먼저 저장하고 이후 `Product` 가격을 바꾸므로, 예외가 `productEntity.changePrice(...)` 전에 발생한다.
따라서 서비스에서 `@Transactional`을 제거해도 이 테스트는 통과할 수 있다. 이 테스트는 “이력 저장이 실패하면 가격 변경 코드가 실행되지 않는다”는 사실은 검증하지만, 가격 변경 뒤 실패했을 때의 DB 롤백은 검증하지 못한다.

학습 목표가 트랜잭션 원자성이라면 실패를 두 변경 작업 이후에 일으키는 테스트 훅이 필요하다. 예를 들어 서비스가 가격 변경과 이력 저장을 모두 수행한 뒤 `flush()`에서 DB 제약 오류가 나도록 구성하거나, 테스트 전용 협력 객체로 두 작업 이후 예외를 발생시켜 별도 영속성 컨텍스트에서 DB 상태를 재조회한다. 구현 순서를 바꾸기보다, “둘 다 실행된 뒤 실패”를 재현하는 것이 핵심이다.

### [P2] 내가 작성한 금액 테스트는 업무 의미와 저장 표현을 분리해야 한다

내가 만든 여러 변경/기간 조회 테스트는 `42000.00` 같은 scale 2의 `BigDecimal.equals`를 기대한다. 컬럼의 `scale = 2`를 학습 대상으로 고정할 의도라면 타당하지만, 가격의 업무적 동일성 검증은 `compareTo`로 해야 한다. 향후 테스트는 다음처럼 나누는 편이 안전하다.

- 가격 변경 여부·이력 값: `isEqualByComparingTo` 또는 `compareTo`.
- DB 컬럼의 소수 두 자리 보존 정책 자체: 별도 테스트에서 `value.scale() == 2`를 명시적으로 검증.

이렇게 하면 DB 표현 정책을 바꾸더라도 핵심 가격 변경 테스트가 불필요하게 깨지지 않는다.

### [P2] `PriceHistory.product`를 DB 차원에서도 필수로 제한한다

이력은 반드시 상품에 속해야 하지만 현재 `@ManyToOne`과 `@JoinColumn`에 필수 제약이 없다. JPA와 DB 스키마에 의도를 남기려면 다음 정책을 고려할 수 있다.

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "product_id", nullable = false)
```

### [P3] 범위 오류는 전용 예외가 더 명확하다

컨트롤러가 `new IllegalArgumentException()`을 던지고 예외 처리기가 모든 `IllegalArgumentException`을 400으로 바꾼다. 현재는 동작하지만, 나중에 프로그래밍 오류성 `IllegalArgumentException`까지 클라이언트 오류로 숨길 수 있다. `InvalidDateRangeException` 같은 전용 예외를 두면 원인과 처리 범위가 분명해진다.

## 추가하면 좋은 테스트

- 두 상품의 이력을 섞어 저장한 뒤, 조회한 상품의 이력만 반환하는지 검증.
- 같은 `changedAt`을 가진 이력의 `id DESC` 보조 정렬 검증.
- `GET` 응답 JSON에서 가격 수치와 시간 형식이 API 계약대로 직렬화되는지 검증.
- DB 컬럼의 scale 2 정책을 유지하기로 했다면 그 정책만 확인하는 전용 테스트.

## 결론

핵심 요구사항은 구현과 현재 테스트에서 충족된다. 다음 학습 우선순위는 “실패 시점이 두 DB 변경 이후가 되도록 만든 롤백 테스트”를 작성해 트랜잭션의 필요성을 실제로 증명하는 것이다. 이 테스트 보강은 내가 처음 제공한 테스트 코드의 개선 과제다.
